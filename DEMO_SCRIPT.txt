SLIDE 3 — WHAT IS A CHANNEL?
-----------------------------
A channel is a thread-safe, async pipe between code that produces data and
code that consumes it. One side calls the Writer to put items in, the other
calls the Reader to take items out. It's first-in, first-out, it's
thread-safe, and critically, it's fully asynchronous. No manual locks, no
Monitor, no SemaphoreSlim, no race conditions to reason about. It's part of
System.Threading.Channels, built right into .NET.

(Point at the diagram — Producer, Writer, Channel<T>, Reader, Consumer.)


SLIDE 4 — THE SIMPLEST CHANNEL CODE
------------------------------------
Three lines is really all it takes. Create the pipe with
Channel.CreateUnbounded<string>(). Write items in with WriteAsync. Read them
out with an await-foreach loop over Reader.ReadAllAsync() — that loop just
keeps running, pulling items as they arrive. Call Writer.Complete() when
you're done producing — that's what tells the reader's await-foreach to end.
Forget that call, and your consumer waits forever.


SLIDE 5 — BOUNDED VS UNBOUNDED
-------------------------------
CreateUnbounded has no capacity limit — the writer never waits, but if your
consumer falls behind, memory grows without bound. That's fine for a quick
console demo, but in production it's a ticking OutOfMemoryException.

CreateBounded, with a number, puts a hard cap on the queue. Once it's full,
the writer pauses — that's backpressure, and it's why you always use bounded
channels in production: predictable memory, automatic flow control.

When the channel is full, the BoundedChannelFullMode setting decides what
happens. Wait — the default — pauses the producer until a slot opens.
DropOldest and DropNewest evict an item instead of waiting. DropWrite
silently discards the new item. We use Wait in our demo today, because we
want to see producers pause.


SLIDE 6 — HANDS-ON PROJECT: THE PROBLEM AND THE SOLUTION
----------------------------------------------------------
Here's the real scenario. A user places an order. The API sends a
confirmation email before responding — and sending an email takes a couple
of seconds. At 500 concurrent requests, that's 500 threads blocked on email
I/O. The thread pool starves, and the whole API stops responding to
everyone, not just the people placing orders.

The fix: the API drops the email onto a Channel<T> and returns instantly —
tens of milliseconds. A separate BackgroundService reads from the channel
and sends emails at its own pace. API threads are never blocked on I/O.


SLIDE 7 — PROJECT ARCHITECTURE
--------------------------------
This is the actual project structure we're about to run. OrderController
writes to the channel. EmailWorker, a BackgroundService, reads from it. The
channel is registered once, as a singleton, so both sides share the exact
same instance through dependency injection. Capacity here is configurable —
we'll use that in a minute to show two different behaviors from the same
code.

(Have Controllers, Models, Services, and Program.cs open in the editor's
file tree so the audience sees the real files.)


SLIDE 8 — ORDERCONTROLLER: THE FAST SIDE
-------------------------------------------
WriteAsync on a channel with room completes in nanoseconds — that's the
whole trick. The controller builds an order ID, drops an EmailMessage onto
the channel, and returns 200 OK immediately. It has zero knowledge of how or
when the email actually gets sent.

(Open Controllers/OrderController.cs and point at the PlaceOrder method.)


SLIDE 9 — EMAILWORKER: THE SLOW SIDE
---------------------------------------
On the other side, EmailWorker is a BackgroundService. It does an
await-foreach over channel.Reader.ReadAllAsync() — that loop asynchronously
waits until an item shows up, processes it, then waits for the next one.
Notice the try-catch around the send: that's essential. If one email throws
and you don't catch it, the exception kills ExecuteAsync, the loop ends,
and the channel silently stops being drained — every order after that
point queues forever with nothing reading it.

(Open Services/EmailWorker.cs and point at the try-catch block.)


SLIDE 10 — WHY USE CHANNELS?
-------------------------------
Four reasons. One: it decouples fast work from slow work — the API responds
instantly, slow work happens in the background, and neither side blocks the
other. Two: the thread pool stays healthy, because threads return to the
pool immediately instead of sitting blocked on I/O. Three: bounded channels
give you flow control for free — no custom throttling code. Four: it's zero
infrastructure — it's part of the .NET runtime. No Redis, no RabbitMQ, no
extra NuGet packages.


SLIDE 11 — WHEN TO USE IT, AND WHEN NOT TO
---------------------------------------------
Use channels for background job queues inside one process, batching writes,
producer-consumer patterns, rate limiting, and decoupling a fast API from
slow I/O — all inside one process.

Don't reach for a channel for cross-process communication, guaranteed
delivery, broadcasting to multiple consumers, durable queues that survive a
restart, or talking between microservices. For that you want RabbitMQ,
Kafka, or Azure Service Bus.

The rule of thumb: channels work inside one service. Message brokers work
between services. Most real systems use both — a channel inside a service,
a broker at the service boundary.


SLIDE 12 — ADVANTAGES
------------------------
Quick highlights: a zero-allocation fast path when there's room in the
buffer, no manual locking, fully async so there are no blocked threads,
built-in backpressure on bounded channels, clean separation between
producer and consumer, and it's lightweight — no infrastructure, no
configuration.


SLIDE 13 — DISADVANTAGES
----------------------------
To be fair about the trade-offs: it's in-memory only, so a crash loses
everything queued. It's single-process — you can't send across machines.
There's no built-in retry — a failed item is just gone unless you code
retry yourself. There's no dashboard or queue-depth metric out of the box,
which is why we built our own channel-status endpoint today. Forgetting to
call Complete() hangs your consumer silently. And an unbounded channel
paired with a fast producer is a memory leak waiting to happen.


SLIDE 14 — PERFORMANCE IMPACT
---------------------------------
Some concrete numbers. API response time is roughly sixty times faster —
from about three seconds down to about fifty milliseconds. Threads blocked
per request goes from N down to zero. Memory per write is essentially zero
allocation, because WriteAsync on the fast path returns a cached ValueTask.

Why this matters under load: without a channel, five hundred concurrent
requests means five hundred threads blocked on email I/O — the thread pool
starves and new requests start timing out. With a channel, those same five
hundred requests return instantly, and only one background worker thread is
doing the actual email work.

If you have a single producer and a single consumer, you can also set
SingleReader and SingleWriter hints on BoundedChannelOptions — that lets the
runtime skip some internal synchronization for even less overhead.

STEP 0 — Start the app

    dotnet run

STEP 1 — One order, with the channel (fast)
----------------------------------------------
Say: "Watch the response time on this one — it should come back almost
instantly, even though sending the email takes two seconds."

    curl -X POST http://localhost:5000/api/orders -H "Content-Type: application/json" -d '{"name":"Akash","email":"akash@test.com"}'

The JSON response (orderId and status "Confirmed") comes back immediately.
A few seconds later, the console shows "Sending email to akash@test.com..."
then "Email sent... (took ~2000ms)" on its own.


STEP 2 — Ten individual requests, still fast
-----------------------------------------------
Say: "Now let's fire ten of these back to back. At the default capacity —
five hundred — the channel never fills up, so every single one should come
back fast."

    for i in $(seq 1 10); do
      curl -s -w " (%{time_total}s)\n" -o /dev/null -X POST http://localhost:5000/api/orders \
        -H "Content-Type: application/json" -d "{\"name\":\"User$i\",\"email\":\"user$i@test.com\"}"
    done

All ten timings land in the single- or low-double-digit milliseconds.
Then run:

    curl http://localhost:5000/api/orders/channel-status

to show the queue still draining in the background, one email every two
seconds.

Say: "Ten orders, all instant, because our channel has plenty of room —
capacity five hundred. The emails are still queued up and sending one at a
time in the background."


STEP 3 — Shrink the capacity, show backpressure
---------------------------------------------------
Say: "Now let's make the channel small on purpose, so we can see
backpressure happen instead of just hearing about it."

Stop the app with Ctrl+C, then restart with a small capacity:

    # bash
    ChannelSettings__Capacity=3 dotnet run

    # PowerShell
    $env:ChannelSettings__Capacity="3"; dotnet run

Then fire ten orders again, all in one burst:

    curl -X POST "http://localhost:5000/api/orders/burst?count=10"

This call now takes several seconds to return, because WriteAsync is
pausing once the three-slot buffer fills. Point at the console log lines —
"Queue: 3/3" repeats while the worker catches up one email at a time.

Say: "That pause you just watched is backpressure. The producer isn't
allowed to pile up unbounded work — it waits for the consumer to make room.
No custom throttling code, no semaphore, no rate limiter. That's the
channel itself protecting the process."


STEP 4 — Compare: without a channel at all
----------------------------------------------
Say: "Last comparison. This endpoint does the exact same order flow, but
skips the channel entirely — it awaits the email send inline before
responding."

    curl -X POST http://localhost:5000/api/orders/slow -H "Content-Type: application/json" -d '{"name":"Akash","email":"akash@test.com"}'

The response takes about two seconds to come back, and includes elapsedMs
in the JSON confirming it.

Say: "Same order, same email, but now the caller pays the full cost of the
slow work. That's the difference a channel makes — not in what work gets
done, but in who has to wait for it."

Say: "So, to recap what we just saw live: one order is instant. Ten orders

SLIDE 16 — KEY TAKEAWAYS
============================
Five things to remember. Channel<T> is a thread-safe async pipe — producer
writes, consumer reads. Always use CreateBounded in production. Call
Complete() when producers are done, or your consumer hangs forever.
Channels work inside a service — use a message broker between services.
And performance-wise: zero-allocation fast path, no thread blocking, and
built-in backpressure, all for free from the .NET runtime.

ANTICIPATED QUESTIONS
========================

Q: Why not just use Task.Run to fire-and-forget the email instead of a
channel?
A: Task.Run gives you no backpressure — unbounded work can pile up — no
ordering guarantee, and an unhandled exception there is much easier to lose
silently. A bounded channel plus one worker gives you a controlled,
observable pipeline instead.

Q: What happens if the process crashes with items still in the channel?
A: They're gone. Channels are in-memory only. If you need durability across
restarts, that's a job for a real queue — RabbitMQ, Azure Storage Queues,
and so on — not System.Threading.Channels.

Q: Can multiple workers read from the same channel?
A: Yes — multiple consumers can call ReadAllAsync concurrently on the same
reader. Items are still delivered to exactly one consumer each, like
competing consumers, not broadcast to all of them.

Q: Does capacity have to be a fixed, hardcoded number?
A: No — ours reads from appsettings.json, or an environment variable,
precisely so you can tune it without a recompile. That's exactly what Step
3 above shows.
