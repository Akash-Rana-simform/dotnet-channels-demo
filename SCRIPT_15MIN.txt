CHANNELS IN .NET — 15 MINUTE SCRIPT
Slides + Demo, all in one
Read this out loud, top to bottom. Total time: about 15 minutes.


SLIDE 1 — TITLE (30 sec)
--------------------------
Today I will show you Channels in .NET. This is a tool that helps two
parts of your code talk to each other. One part sends work. The other
part does the work. They do not wait for each other.


SLIDE 2 — AGENDA (30 sec)
----------------------------
Here is the plan. First, I will explain what a Channel is. Then I will
show you a real project. Then we will run it live and see it work.


SLIDE 3 — WHAT IS A CHANNEL? (1 min)
---------------------------------------
A Channel is like a pipe. One side puts items in. The other side takes
items out. It is safe to use from many places at once. It works with
async code, so nothing gets stuck waiting. It is built into .NET, so you
do not need any extra tool.


SLIDE 4 — SIMPLE CHANNEL CODE (1 min)
----------------------------------------
The code is short. You create a Channel. You write items into it. You
read items out of it in a loop. When you are done writing, you call
Complete(). If you forget that, the reader will wait forever.


SLIDE 5 — BOUNDED VS UNBOUNDED (1 min)
-----------------------------------------
A Channel can have no limit. This is called unbounded. It is easy but
risky, because it can use too much memory.

A Channel can also have a limit. This is called bounded. When it is
full, the writer waits. This is called backpressure. Always use a
bounded Channel in real projects.


SLIDE 6 — THE PROBLEM AND THE FIX (1 min)
--------------------------------------------
Here is our example. A user places an order. The app sends an email.
Sending an email is slow, about two seconds. If many users order at the
same time, the app gets stuck waiting on emails.

The fix: put the email job into a Channel. The app replies right away.
A separate worker sends the emails in the background.


SLIDE 7 — PROJECT PARTS (30 sec)
-----------------------------------
Our project has two main parts. The Controller writes new emails into
the Channel. The Worker reads emails from the Channel and sends them.
Both parts share the same Channel.


SLIDE 8 — THE FAST SIDE (30 sec)
-----------------------------------
This is the Controller code. It builds an order. It puts the email in
the Channel. Then it replies right away. It does not wait for the email
to be sent.


SLIDE 9 — THE SLOW SIDE (1 min)
-----------------------------------
This is the Worker code. It waits for new emails, one at a time. When
one comes in, it sends it. This takes about two seconds. There is a
try-catch around this step. If one email fails, the Worker keeps
running. Without this, one bad email would stop everything.


SLIDE 10 — WHY USE CHANNELS (30 sec)
---------------------------------------
Four reasons. It splits fast work from slow work. It keeps your app's
threads free. It controls how much work can pile up. And it needs no
extra software, since it is built into .NET.


SLIDE 11 — WHEN TO USE IT (30 sec)
-------------------------------------
Use it inside one app, for one background job, or to slow down fast
input. Do not use it to send data between two different apps or two
different servers. For that, use a tool like RabbitMQ instead.


SLIDE 12 — GOOD POINTS (30 sec)
-----------------------------------
It is fast, it is safe, it does not block threads, and it needs no
setup.


SLIDE 13 — WEAK POINTS (30 sec)
-----------------------------------
If the app crashes, queued items are lost. It only works inside one
app. It has no built-in retry. And if you forget to call Complete(),
your app can hang.


SLIDE 14 — SPEED NUMBERS (30 sec)
-------------------------------------
With a Channel, replies are about sixty times faster. Before: about
three seconds. After: about fifty milliseconds. We will see this live
in a moment.


SLIDE 15 — LIVE DEMO (5 min)
================================
Now let's run it together.


DEMO STEP 1 — Start the app (30 sec)
---------------------------------------
Run this:

    dotnet run

Wait for this line: "Now listening on http://localhost:5000"
Open this in a browser: http://localhost:5000/swagger


DEMO STEP 2 — One fast order (1 min)
----------------------------------------
Say: "Watch how fast this reply comes back."

Open POST /api/orders in Swagger. Click "Try it out". Use this text:

    { "name": "Akash", "email": "akash@test.com" }

Click "Execute". Show the reply. It says elapsedSeconds, a very small
number, like 0.01. The email is not sent yet. It sends in the
background, about two seconds later. You will see it in the console
window.


DEMO STEP 3 — Show backpressure (2 min)
-------------------------------------------
Say: "Now let's make the Channel small, so we can see it push back."

Stop the app. Start it again with a small Channel size:

    ChannelSettings__Capacity=3 dotnet run

In Swagger, open POST /api/orders/burst. Click "Try it out". Set count
to 10. Click "Execute".

Say: "Watch the console. The first three orders go in fast. Then it
waits for the worker to catch up."

Show the reply. elapsedSeconds is now a much bigger number, several
seconds. This is backpressure. The Channel is full, so new writes wait.


DEMO STEP 4 — Compare: no Channel at all (1 min 30 sec)
-----------------------------------------------------------
Say: "Now let's see what happens without a Channel."

Open POST /api/orders/slow in Swagger. Same input as before. Click
"Execute".

Say: "Watch it. This one waits for the whole two seconds before it
replies."

Show elapsedSeconds. It will be about 2.0. Compare it out loud to the
first number from Step 2. Same work, very different wait time.


SLIDE 16 — KEY POINTS TO REMEMBER (30 sec)
----------------------------------------------
A Channel is a safe pipe between two parts of your code. Always use a
bounded Channel. Always call Complete() when you are done writing. Use
Channels inside one app, not between apps.
